# 建筑资质公开信息监测与归档系统 V2 详细设计

## 1. V2 定位

V1 已完成“抓得到、存得住、看得见、能通知、可追溯”的本机端到端闭环。V2 的目标是在 V1 归档数据之上，建设一个轻量本地知识库 MVP，让已抓取公告、正文和附件可以被解析、检索、引用，并通过后台和企微完成最小问答闭环。

V2 不追求一次性做成完整智能申报系统，而是先验证三个核心问题：

- 附件内容是否能稳定解析并入库。
- 用户是否能用关键词快速找到公告、附件和原始来源。
- 企微里是否能提出简单问题并拿到可追溯的本地知识库结果。

## 2. V2 MVP 范围

### 2.1 本阶段做

- 解析已下载的 PDF、Word、Excel 附件文本。
- 记录附件解析状态、错误原因、解析时间、文本长度、解析器名称。
- 支持手动解析单个附件、批量解析未解析附件、抓取完成后可选自动解析。
- 建立轻量本地关键词检索能力。
- 支持检索公告标题、公告正文、附件名称、附件解析文本。
- 后台新增统一检索页面。
- 公告详情和附件详情展示解析状态与解析文本摘要。
- 提供简单知识库 API：`POST /api/kb/search`。
- 提供最小问答 API：`POST /api/kb/ask`，先基于关键词检索返回结果摘要，不接大模型生成。
- 提供 OpenClaw / 企微问答最小入口：可接收问题文本，返回检索结果摘要和后台链接。
- 增加 V2 自动验收命令：`zhengfudata v2-acceptance-check`。

### 2.2 本阶段不做

- 不做向量数据库。
- 不做复杂 RAG。
- 不接 OpenAI 或其他大模型生成最终答案。
- 不做资质标准库。
- 不做企业档案。
- 不做企业资质申报辅助。
- 不生成资质分析报告。
- 不生成申报材料 Word / Excel。
- 不做复杂多轮会话记忆。
- 不做 OCR 扫描件识别，除非 PDF 自带文本。
- 不做云端对象存储。

## 3. 用户场景

### 3.1 后台检索

用户进入后台“知识库检索”，输入关键词，例如：

```text
建筑业企业资质延续
安全生产管理人员成绩
施工总承包二级
```

系统返回：

- 命中的公告。
- 命中的附件。
- 命中来源：标题、正文、附件名、附件解析文本。
- 命中片段。
- 原始地址。
- 后台详情链接。
- 附件下载入口。

### 3.2 附件解析

用户在附件管理页看到附件解析状态：

- 未解析
- 解析中
- 解析成功
- 解析失败
- 不支持

用户可以手动点击“解析”，也可以批量解析未解析附件。

### 3.3 企微问答

用户在企微发送：

```text
查一下最近建筑业企业资质延续公告
```

系统返回最多 5 条检索结果：

```text
找到 5 条相关信息：
1. 住房城乡建设部关于核准2026年度第六批建设工程企业资质延续名单的公告
   来源：住房和城乡建设部 / 公告
   命中：标题
   后台：http://127.0.0.1:8000/announcements/...
   原文：https://...
```

V2 的“问答”本质是可追溯检索摘要，不编造结论。

## 4. 总体架构

```text
V1 数据
  ├─ announcements 正文
  ├─ attachments 本地文件
  └─ attachment_versions 历史版本
        ↓
附件解析服务
        ↓
document_texts / search_index
        ↓
关键词检索服务
        ↓
后台检索页面 + API
        ↓
OpenClaw 企微问答入口
```

## 5. 数据模型设计

### 5.1 document_texts 附件解析文本表

用于保存附件文件解析后的文本。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | integer | 主键 |
| attachment_id | integer | 附件 ID |
| attachment_version_id | integer nullable | 附件版本 ID |
| source_type | string | `attachment` |
| parser_name | string | 解析器名称，如 `pdf_text`、`docx_text`、`xlsx_text` |
| parser_version | string | 解析器版本 |
| status | string | `pending` / `running` / `success` / `failed` / `unsupported` |
| text | text | 解析后的纯文本 |
| text_hash | string | 文本 hash |
| text_length | integer | 文本长度 |
| error_message | text nullable | 失败原因 |
| parsed_at | datetime nullable | 解析完成时间 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |

约束：

- 同一个 `attachment_version_id` 最多保留一条成功解析记录。
- 如果附件内容 hash 未变化，不重复解析。
- 解析失败保留错误原因，便于后台排查。

### 5.2 search_index 轻量检索索引表

SQLite 不强依赖 FTS5，先采用普通表 + LIKE 检索，降低 Windows 部署风险。后续如确认运行环境支持 FTS5，再升级为 FTS 虚表。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | integer | 主键 |
| entity_type | string | `announcement` / `attachment` |
| entity_id | integer | 对应实体 ID |
| title | string | 标题 |
| body | text | 可检索文本 |
| source_url | string | 原始地址 |
| backend_path | string | 后台路径 |
| site_name | string | 来源网站 |
| section_name | string | 来源栏目 |
| published_at | datetime nullable | 发布时间 |
| updated_at | datetime | 索引更新时间 |

索引策略：

- 公告入库或变化后更新公告索引。
- 附件解析成功后更新附件索引。
- 支持命中类型标记：标题、正文、附件名、附件文本。

## 6. 附件解析模块

### 6.1 支持格式

V2 支持：

- PDF：优先提取文本型 PDF。
- Word：支持 `.docx`。
- Excel：支持 `.xlsx`、`.xls` 如依赖可用。

V2 暂不支持：

- 图片 OCR。
- 加密文件。
- 损坏文件。
- 复杂版式还原。

### 6.2 推荐依赖

优先选用纯 Python 或轻量依赖：

- PDF：`pypdf`。
- Word：`python-docx`。
- Excel：`openpyxl`。

如果当前环境已有更适合的库，可在实现时根据 `pyproject.toml` 最小化新增依赖。

### 6.3 解析流程

```text
选择附件
  ↓
检查本地文件存在
  ↓
按扩展名选择解析器
  ↓
提取纯文本
  ↓
写入 document_texts
  ↓
更新 search_index
```

### 6.4 失败处理

- 文件不存在：`failed`，记录本地路径缺失。
- 格式不支持：`unsupported`。
- 解析异常：`failed`，记录异常类型和简短错误。
- 解析文本为空：`success`，但 `text_length=0`，后台显示“未提取到文本”。

## 7. 检索模块

### 7.1 检索范围

- 公告标题。
- 公告正文。
- 附件名称。
- 附件解析文本。
- 来源网站。
- 栏目名称。

### 7.2 检索规则

V2 使用简单关键词检索：

- 用户输入按空格拆词。
- 中文连续文本不强制分词，先整体 LIKE 匹配。
- 多关键词默认 AND。
- 返回按简单权重排序：
  - 标题命中权重最高。
  - 附件名称命中次之。
  - 正文和附件文本命中再次。
  - 发布时间越近略微加权。

### 7.3 返回结果

每条结果包含：

- `entity_type`
- `entity_id`
- `title`
- `snippet`
- `match_fields`
- `site_name`
- `section_name`
- `published_at`
- `source_url`
- `backend_url`

## 8. API 设计

### 8.1 POST /api/kb/search

请求：

```json
{
  "query": "建筑业企业资质延续",
  "limit": 10
}
```

响应：

```json
{
  "query": "建筑业企业资质延续",
  "total": 3,
  "items": [
    {
      "entity_type": "announcement",
      "entity_id": 1,
      "title": "住房城乡建设部关于核准...",
      "snippet": "...建筑业企业资质延续...",
      "match_fields": ["title", "body"],
      "source_url": "https://...",
      "backend_url": "http://127.0.0.1:8000/announcements/1"
    }
  ]
}
```

### 8.2 POST /api/kb/ask

V2 的 ask 不调用大模型，只返回检索摘要。

请求：

```json
{
  "question": "最近建筑业企业资质延续公告有哪些？",
  "limit": 5
}
```

响应：

```json
{
  "question": "最近建筑业企业资质延续公告有哪些？",
  "answer_type": "search_summary",
  "answer": "找到 5 条相关信息，请以原文和附件为准。",
  "items": []
}
```

### 8.3 POST /api/openclaw/kb/ask

用于 OpenClaw 调用。

请求：

```json
{
  "text": "查一下最近建筑业企业资质延续公告",
  "source": "wecom"
}
```

响应：

```json
{
  "text": "找到 5 条相关信息：\n1. ..."
}
```

## 9. CLI 设计

新增命令：

```text
zhengfudata parse-attachments --limit 20
zhengfudata parse-attachment <attachment_id>
zhengfudata rebuild-search-index
zhengfudata kb-search "建筑业企业资质延续"
zhengfudata v2-acceptance-check
```

命令说明：

- `parse-attachments`：批量解析未解析或解析失败的附件。
- `parse-attachment`：解析单个附件。
- `rebuild-search-index`：重建公告和附件检索索引。
- `kb-search`：命令行检索，便于验收和排障。
- `v2-acceptance-check`：自动执行 V2 验收检查。

## 11. OpenClaw 企微问答设计

V2 先采用主动 HTTP 调用模式，不要求 OpenClaw 深度托管业务逻辑。

推荐接入方式：

- OpenClaw 收到企微消息。
- OpenClaw 将文本 POST 到本系统 `/api/openclaw/kb/ask`。
- 本系统返回文本摘要。
- OpenClaw 回复企微。

若 OpenClaw 当前没有方便配置 HTTP 回调，则 V2 先完成本系统 API 和 CLI 问答，企微问答作为人工联调项。

## 13. 开发顺序

- 新增 `document_texts` 表。
- 新增 `search_index` 表。

验收：

- 迁移可执行。
- 表结构存在。
- 现有 V1 测试不回退。

### M2 附件解析服务

- 实现 PDF / DOCX / XLSX 解析器。
- 实现单附件解析。
- 实现批量附件解析。
- 写入解析状态和错误原因。

验收：

- 能解析至少一个本地 PDF、Word、Excel 样例。
- 不支持或失败文件有明确错误。
- 本地无文件附件不导致任务崩溃。

### M3 检索索引服务

- 公告索引构建。

- 关键词搜索服务。

验收：

- 可搜索附件名称。

### M4 后台检索页面

- 新增知识库检索页。

## 14. V2 验收条件

V2 交付验收必须满足：

- `doctor` 通过。
- `ruff check .` 通过。
- `ruff format --check .` 通过。
- `pytest` 通过。
- 至少 1 个 PDF 附件解析成功。
- 至少 1 个 Word 附件解析成功，若当前真实附件没有 Word，可用测试样例验证解析器。
- 至少 1 个 Excel 附件解析成功，若当前真实附件没有 Excel，可用测试样例验证解析器。
- `kb-search` 能搜索到公告标题。
- `kb-search` 能搜索到附件解析文本。
- `/api/kb/search` 返回 200。
- `/api/kb/ask` 返回 200。
- `/api/openclaw/kb/ask` 返回 200。
- `/kb/search` 后台页面返回 200。
- 附件管理页展示解析状态。
- V1 抓取、附件下载、企微日报通知不回退。

## 15. 风险与处理

### 15.1 真实附件格式复杂

风险：政府附件可能包含扫描 PDF、旧版 Word、合并单元格 Excel。

处理：

- V2 先保证文本型 PDF、DOCX、XLSX。
- 对无法解析文件标记 `unsupported` 或 `failed`。
- OCR 放入 V3。

### 15.2 SQLite LIKE 检索效果有限

风险：中文检索召回不如专业搜索引擎。

处理：

- V2 先做可用关键词检索。
- 后续再评估 SQLite FTS5、Whoosh、Meilisearch 或向量库。

### 15.3 OpenClaw 入站问答集成不确定

风险：OpenClaw 当前环境已完成企微发送，但入站消息回调方式需要再联调。

处理：

- V2 先实现本系统 API。
- 企微问答联调作为独立验收项。
- 如果入站回调不可用，先通过 CLI 或手动 HTTP 完成问答验证。

## 16. 确认点

进入开发前需要确认：

- V2 是否以“本地关键词知识库”为第一目标，而不是直接接大模型。
- 是否接受 V2 暂不做 OCR。
- 是否接受 V2 暂不做资质报告生成。
- 是否接受 OpenClaw 企微问答先以 API 联调为准，真实群内问答作为后续增强验收。
